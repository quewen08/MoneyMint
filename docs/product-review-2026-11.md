# FamBean 产品诊断与版本路线图

> 版本：**v2.1** ｜ 日期：2026-11-03 ｜ 视角：产品诊断 + 方向决策
> 盘点基线：`CHANGELOG.md`（0.4.0，2026-08-20）+ `docs/change-plan-0.4.md` + 代码实测（`internal/`、`frontend/lib/`）
> **v2.0 变更**：老板已就 5 个关键问题拍板（见 §0），据此裁掉公网安全重投入、锁定 Beancount 生态主线、排期改为「可中断里程碑」结构。
> **v2.1 变更**：M0 范围扩展为「工程护栏 + 容器化」（GitHub Actions → Docker Hub），M0/M1 工作量按实测上调（含 3 项新发现的坑：`bean-check` 假绿灯、SQLite WAL 备份残缺、前端静态托管缺失）；详细拆解见 `docs/m0-m1-requirements.md`。

## 〇、已确认决策（2026-11-03，老板拍板）

| # | 问题 | 决策 | 对方案的影响 |
|---|---|---|---|
| D-1 | 给谁用 | **自己 + 家人**，合适可公开 | 备份恢复从「重要」升为「不可省」——家人的账不能丢；公开前需过 §7 的公开阈值表 |
| D-2 | 网络形态 | **主做内网**，外网由用户自备代理/远程工具 | **砍掉** HTTPS/反代/公网审计这一整块投入；部署文档给说明即可，不做产品化 |
| D-3 | 移动端 4 Tab | 合适就做 | 从 Must 降为 Should，随 M6 打磨一起做 |
| D-4 | 差异化方向 | **Beancount 生态** | v0.7 主线确定：导入、导出互通、元数据完整、与生态工具互操作 |
| D-5 | 节奏 / 上线时间 | 时间不固定，**不急上线** | 排期改为「可中断里程碑」：每个包 1~3 天可独立完成、独立验收、随时能停能续 |

**决策带来的三个连锁判断**：

1. **安全要求降级**：内网为主 → 不需要为公网攻击面做设计。但**强制改默认密码、登录失败限流、会话可吊销**这三项仍要做——因为家庭内网也有共用设备、访客 WiFi、设备丢失场景，成本极低。
2. **备份优先级反而升到最高**：不急上线 ≠ 不急着保护数据。家人一旦开始记，数据只增不减，丢一次就是灾难。
3. **排期不能按周**：时间碎片化 + 不急，反而最怕「开了个大功能做一半」。必须切成能随时停下的独立片。

## 一、结论先行

**一句话判断**：账芯扎实、骨架完整；但「数据自持」的核心承诺只兑现了一半——**能带走，但丢不起、回不来**。

**三件必须先做的事**：

| # | 事项 | 为什么 |
|---|---|---|
| 1 | **自动备份 + 一键下载** | 数据自持 = 责任自持。SQLite 单文件 + NAS 单盘，一次损坏全家账目归零 |
| 2 | **Beancount 导入 + 恢复** | 承诺的闭环断点。导出的账本回不来、备份了也回不去，等于没做 |
| 3 | **强制改默认密码 + 登录限流** | 半天成本，把「不敢给家人开账号」变成「可以开」 |

**方向**：不再追消费级记账 App 的标配功能，**全力押 Beancount 生态**——把「录入」做顺，把「互通」做透，分析和可视化交给生态工具（Fava / `bean-query` / 脚本）。这是唯一别人抄不走的路线。

## 三、不足诊断

### 3.1 P0 · 阻断级（家人开始用之前必须解决）

| 编号 | 不足 | 证据 | 影响 |
|---|---|---|---|
| G-01 | **无备份机制** | `grep backup/restore/snapshot` 在 `internal/`、`frontend/lib/` 零命中 | NAS 磁盘故障 / 误操作 / 迁移失败 = 全部历史不可恢复。**数据自持产品的一号红线** |
| G-02 | **无恢复能力** | 无 restore 端点、无导入功能 | 备份了也回不去，等于没备份 |
| G-03 | **只能导出不能导入** | 端点仅 `/api/export`、`/api/export/archive` | ① 老账本迁不进 ② 自家导出回不来 ③ 换机只能靠原始 db 文件 |
| G-06 | **误删不可恢复** | 前端 `local_store.deleteTxn` 本地硬删；服务端软删但**无恢复端点、无回收站** | 误删一笔 = 前端视角永久消失；服务端数据滞留成脏数据 |
| G-07 | **首次启动无强制改密** | 迁移 002 置 owner 密码为 `owner123456` | 默认凭据公开已知，用户大概率不改就开用 |

### 3.2 P1 · 可靠性与安全（内网场景下的合理水位）

| 编号 | 不足 | 说明 | 内网下是否仍要做 |
|---|---|---|---|
| G-04 | 认证无防暴破 | 无失败计数/限流/锁定，token 30 天长效 | **要做**（成本低；共用设备与访客 WiFi 场景真实存在） |
| G-04b | 会话不可管理 | 无会话列表、无法踢掉丢失设备 | **要做**（低成本，替代方案是改密码全踢） |
| G-05 | 无部署物 | 仅有 `.dockerignore`，无 Dockerfile/compose | **降级**：给一份 compose + 说明即可，不做产品化 |
| G-11 | 忘记密码死锁 | 仅 owner 能重置成员；owner 自己忘密码无解 | **要做**（家人用，这是高频事故） |
| G-12 | 账本无删除/归档/交接 | 只能创建/改名/切换 | Should（家人场景 owner 变更会真实发生） |

### 3.3 P2 · 体验与留存（决定「能不能坚持记」）

| 编号 | 不足 | 说明 |
|---|---|---|
| G-08 | 移动端仍 3 Tab | `mobile_shell.dart` 为「首页/流水/我的」，资产页埋在二级入口 |
| G-09 | 无周期记账 | 房租/房贷/工资/物业/订阅——家庭账本里重复条目占比极高（估算，待实测），现在全靠每月手录 |
| G-10 | 无预算 | 家庭记账第一诉求是「这个月还能花多少」。没预算，记账只是事后凭证 |
| G-13 | 报表维度偏薄 | 缺同比/环比、按成员、按标签下钻 |
| G-14 | 无批量操作 | 批量改分类/加标签/删除均无 |
| G-19 | 搜索纯前端过滤 | 家庭量级够用，过万条会卡 |

### 3.4 P3 · Beancount 生态缺口（差异化主战场）

> 这组是 v2.0 新增的核心判断：既然押 Beancount 生态，这些缺口就是**长板没打出去**，不是「锦上添花」。

| 编号 | 不足 | 说明 |
|---|---|---|
| G-25 | **生态单向** | 只能导出，不能接收任何外部 Beancount 文件。生态地位=生产者，不是参与者 |
| G-26 | **未知指令会丢** | 导入他人的 `.beancount` 时，不认识的指令（`plugin`/`include`/`custom`/`note`/`document` 等）若无原样保留机制，账本会被静默污染（**待实测确认**当前是否有该风险） |
| G-27 | **元数据不完整** | 导出未充分利用 Beancount 的 `payee` / `links` / `meta`，导致 `bean-query` 与生态工具的分析能力打折 |
| G-28 | **校验依赖外力** | 结构正确性只靠手动跑外部 `bean-check`，产品内无自检能力 |
| G-29 | **生态工具未验证互通** | 未验证导出文件能否被 Fava / `bean-query` 直接消费（**待验证假设**，若成立则等于免费获得专业分析层） |

### 3.5 P4 · 工程级（决定能改多快、敢改多狠）

| 编号 | 不足 | 证据 | 影响 |
|---|---|---|---|
| G-20 | 测试覆盖极低 | 后端仅 `beancount_test.go`、`service_test.go`；前端仅 `widget_test.dart` | 账芯改动全靠手测，`bean-check` 靠人记得跑 |
| G-21 | 无 CI | 无 workflows / Makefile / justfile | 回归不可重复 |
| G-22 | 无迁移回滚演练 | 框架幂等（做得好），但未验证迁移失败如何回退 | 一次坏迁移 = 数据事故 |
| G-23 | 无运行时可观测 | 无结构化日志/健康指标/错误上报 | NAS 上出问题只能看 stdout |
| G-24 | 文档与代码漂移 | `AGENTS.md` §7 未含 `op=update`/`op=close`；0.4-D 状态标记与实际不符（流水筛选/搜索/记账人/日历已实现，仅 4 Tab 未做） | 过几天自己都会误判 |

## 四、深层问题（比功能清单更重要）

### 4.1 承诺与实现的缺口，是信任缺口而不是功能缺口

对外三个卖点：数据自持 / 离线优先 / 标准兼容。现状是「数据在你手上，一旦出事我救不回来」。**功能可以慢慢加，信任塌了没有第二次。**

### 4.2 之前的路线在拿短板碰别人的长板

近两个版本：饼图、双线趋势、月历、拖拽排序、默认账户。全是商业 App 的标配。这条赛道打不赢——对面是全职团队。而 FamBean 独有的是**复式可审计 + Beancount 可编程 + 数据可自由迁移**。

D-4 已确认押后者，本路线图据此重排。

### 4.3 缺一个「不靠自律也能活」的钩子

家庭记账的真实死因不是图表不好看，是**记三天就没人记了**。现在没有周期记账、没有预算、没有家庭反馈——功能过了及格线，留存机制是零。

### 4.4 单人全栈 + 近乎零测试 + 无 CI = 账芯风险不可控

`bean-check` 是唯一防线，且靠人肉跑。这是最大单点风险。

## 五、方向与路线图（可中断里程碑结构）

### 5.1 为什么改成里程碑而不是版本

D-5 明确「时间不固定、不急上线」。传统按周排期在这种节奏下必然烂尾——最怕开了个大功能做到一半卡住两周，回来连自己写到哪都忘了。

所以切成 **M0~M6 七个里程碑**，每个满足三条硬要求：

- **1~3 天可完成**（碎片时间也能推进）
- **独立可交付**（做完就能用，不依赖后续）
- **独立可验收**（有明确的「怎么算做完了」，可自测）
- **可随时中断**（停下来不产生半成品状态）

### 5.2 里程碑清单

| 编号 | 里程碑 | 工作量（估算，自然日） | 依赖 | 独立验收口径 |
|---|---|---|---|---|
| **M0** | **工程护栏 + 容器化**：`bean-check` 严格化 + Go 托管前端静态产物 + 多阶段 Dockerfile + compose + GitHub Actions 推 DockerHub（双架构）+ Makefile | **2~2.5** | — | 一条命令构建镜像并跑完全套检查；tag 推送产出 amd64/arm64 镜像；账芯改坏 CI 即红 |
| **M1** | **备份底座**：一致性快照（WAL 安全）+ 定时/补跑 + 保留策略 + 系统管理员角色 + 一键下载 | **2~2.5** | M0 | 快照含 WAL 未落盘数据且 `integrity_check` 通过；管理员可列/下/手动备份 |
| **M2** | **恢复 + Beancount 导入**：上传备份包还原（还原前自动快照）+ 导入 `.beancount`（自家格式优先） | 2~3 | M1 | 导入自家导出的文件后，账户数/交易数/余额一一对应；还原后 `bean-check` 通过 |
| **M3** | **可用门槛**：强制改默认密码 + 登录失败限流 + 会话列表与吊销 + 交易回收站 | 2 | M0 | 默认凭据首次登录必须改密；连错 N 次冷却；误删交易可在回收站找回且余额正确 |
| **M4** | **Beancount 生态深化**：导出元数据补全（payee/links/meta）+ 未知指令原样保留 + 内置结构自检 + 生态工具互通实测 | 2~3 | M2 | 导入含 `plugin`/`include`/`custom` 的外部文件后原样可导出；导出文件被生态工具正常消费（实测结论留档） |
| **M5** | **留存机制**：周期记账（模板 + 到期生成）+ 分类月度预算 + 超支提示 | 5~6（可再切两半） | M3 | 周期模板到期自动生成且离线补生成正确；预算超支有明确提示 |
| **M6** | **打磨收尾**：移动端 4 Tab + 忘记密码自助重置 + 报表维度（同比/环比/按成员）+ 文档校订 | 3~4（可再切） | — | 4 Tab 各页正常；重置密码可自助完成；`AGENTS.md` 与代码一致 |

> 工作量单位为单人自然日，含自测，不含返工。**均为估算**，随实际推进修正。

### 5.3 推荐执行顺序与理由

```
M0 → M1 → M2 → M3 →（此线完成 = 家人可以安心用）
        ↓
       M4 →（差异化立住）
        ↓
       M5 → M6（留存与打磨）
```

**为什么 M0 排第一**：成本半天，但立刻给后面所有工作装上安全网。账芯改坏了 CI 会拦住，不用靠记忆。

**为什么 M1/M2 是「家人可用」的分界线**：这两条做完，产品从「自己玩、丢了算自己的」变成「可以给家人开账号、出事能救」。这是 D-1 的直接推论。

**为什么 M3 紧接 M1/M2 而不是最后**：半天到两天成本，换掉「默认密码公开」这个隐患。给家人开账号前必须过。

**为什么 M4 在 M5 之前**：D-4 已定 Beancount 生态为主线。M4 是低成本高杠杆（元数据补全、未知指令保留、互通验证），先把手里的牌打亮，再去做留存功能。

**为什么 M5 可以缓**：它是对抗「记三天就放弃」的关键，但只有家人**已经在用了**才有意义。用都没开始，先做预算是本末倒置。

### 5.4 如果精力极度碎片化，最小可用序列

只做 **M1-a（系统管理员）+ M1-b/c（快照引擎与定时）+ M3 里的强制改密**（合计约 2~3 天），就能达到「可以给家人开账号、数据丢了能救」的最低安全线。其余全部可延后——但 **M0-a（`bean-check` 严格化）建议提前到最前面**，它只花半天且保护后续所有改动。

> 详细拆解见 `docs/m0-m1-requirements.md`（含 10 个原子任务、功能规则与验收标准）。

## 六、Beancount 生态路线（D-4 展开）

既然差异化锁定生态，具体打法是「**不做分析，做录入入口 + 互通枢纽**」：

| 层次 | 做什么 | 为什么 |
|---|---|---|
| **入口** | 随手记账体验要好、要快、要能离线 | 生态里缺一个「普通人愿意每天用」的录入前端。专业工具（文本编辑器 + Fava）录入成本高 |
| **互通** | 导入任意合法 `.beancount`；导出能被生态工具直接吃下 | 成为生态的**双向节点**，而不是只出不进的孤岛 |
| **保真** | 不认识的指令原样保留、不明字段不丢、账本不被静默改写 | 这是生态兼容的技术底线。破坏一次，别人就再也不信你的导出 |
| **互操作** | 验证与 Fava / `bean-query` / 脚本的配合（**待实测，若成立则免费获得整个专业分析层**） | 用别人的长板补自己的短板，比自建图表划算得多 |
| **自检** | 产品内置结构校验（不平衡、孤立 posting、日期越界等），导出前就拦截 | 把「必须过 bean-check」从外部约束变成产品能力 |

**明确不做**：自建复杂分析引擎、对标 Fava 的可视化。这块交给生态。

## 七、公开阈值（D-1「合适可公开」的前置条件）

现在不用做，但边界要清楚。**未全部满足前不建议对陌生人开放注册**：

| # | 条件 | 当前状态 | 落在哪个里程碑 |
|---|---|---|---|
| 1 | 备份 + 恢复可用 | ❌ | M1 / M2 |
| 2 | 导入可用（用户能带走也能带回） | ❌ | M2 |
| 3 | 强制改默认密码 | ❌ | M3 |
| 4 | 登录限流与失败锁定 | ❌ | M3 |
| 5 | HTTPS（公开后公网必过） | ❌ | 公开前专项 |
| 6 | 注册控制（邀请制 / 关闭自由注册） | ❌ | 公开前专项 |
| 7 | 资源配额与滥用防护（磁盘/请求量） | ❌ | 公开前专项 |
| 8 | 多用户数据隔离回归验证 | ⚠️ 设计已有（`X-Ledger-Id`），未做越权回归 | 公开前专项 |
| 9 | 隐私说明与数据去向告知（自持产品也要说清） | ❌ | 公开前专项 |

> 提示：**第 1~4 项是家人可用线，第 5~9 项是公开线**。两条线不要混着做，否则会把内网阶段拖成公网工程。

## 九、如果只做三件事

按顺序做这三件，产品性质就变了：

1. **`bean-check` 严格化 + CI**（0.5~1 天）→ 账芯从「靠人记着跑」变成「机器把关」，且不再假绿灯
2. **一致性快照备份 + 一键下载**（1.5~2 天）→ 从「随时可能全丢」变成「丢了能救」
3. **强制改默认密码 + Beancount 导入**（1~2 天）→ 从「不敢开门」变成「能给家人开账号」，且承诺闭环

剩下的都可以等。
