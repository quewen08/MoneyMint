# FamBean M2 开发方案：备份还原 + Beancount 导入

> 版本：v1.0 ｜ 日期：2026-11-03
> 上游：`docs/product-review-2026-11.md` v2.1（路线图 M2）+ M1 已交付（备份底座）
> 性质：方案 + 任务拆解。含 3 个需拍板的决策，其余按推荐值推进。

---

## 一、先给结论：技术前提已实测验证

恢复最大的疑问是「能不能在不停机、不替换文件的前提下安全还原」。已验证通过：

| 验证项 | 结果 |
|---|---|
| `ATTACH DATABASE ? AS bak` 参数化路径 | ✅ 可用 |
| `PRAGMA foreign_keys=OFF` 在事务外生效 | ✅ 生效 |
| 事务内逐表 `DELETE` + `INSERT SELECT` 替换 | ✅ 12 张表全部成功 |
| 数据完全被备份覆盖、旧数据清除干净 | ✅ |
| `sqlite_sequence` 自增计数器随数据更新 | ✅ 还原后写入正常 |
| 事务失败自动回滚 | ✅ 由事务保证 |

**结论**：恢复走「ATTACH + 事务内逐表替换」，不动数据库文件、不需要停机、失败自动回滚。

> 反例说明为什么不用「复制文件覆盖」：运行中的 SQLite 连接持有文件句柄，覆盖文件在 Linux 上会替换 inode、在 Windows 上直接失败；而且 WAL 模式下还有 `-wal`/`-shm` 需要一并处理。风险远高于逐表替换。

## 二、范围

| 项 | 内容 | 归属 |
|---|---|---|
| **恢复** | 从 `.db` 备份还原全库（服务端已有备份 + 上传外部文件两种入口） | M2 主线 |
| **导入** | 解析 `.beancount` 文本并写入（自家导出格式优先） | M2 主线 |
| 恢复前的安全网 | 还原前自动快照（`trigger=pre-restore`） | M2 必须 |
| 通用 Beancount 语法（cost/price 注解、pad/balance、include/plugin） | 不支持，明确报错 | M4 |
| 未知指令原样保留 | 属于生态保真 | M4 |

## 三、需拍板的 3 个决策

### D-1 恢复的粒度

| 方案 | 说明 | 风险 | 推荐 |
|---|---|---|---|
| **A. 全库还原** | 替换 users/ledgers/accounts/transactions 等全部表 | 会替换用户表，**当前登录态失效**，需用备份里的账号重新登录 | ✅ **推荐** |
| B. 单账本还原 | 只替换某一账本的数据 | 需要处理用户/成员映射、跨表引用，复杂度高 | 后续版本 |

**推荐 A**，理由：备份本身就是全库产物（M1 的设计），单账本还原需要重新定义"账本边界"，且备份文件里没有"只取某账本"的可靠切分依据。

⚠️ **必须让用户知道**：还原后当前账号会消失（若备份里没有该账号），要用备份时期的账号登录。这是 A 方案唯一但重要的副作用，必须在 UI 上写清楚。

### D-2 导入的目标位置

| 方案 | 说明 | 冲突处理 | 推荐 |
|---|---|---|---|
| **A. 新建账本** | 导入时创建新账本，原数据完全不动 | 零冲突 | ✅ **推荐** |
| B. 合并到现有账本 | 账户按名合并、交易追加 | 需处理同名账户、重复交易、日期冲突，Beancount 文件无 uuid 无法判重 | 后续版本 |
| C. 清空后导入 | 类似恢复 | 破坏性，且与"恢复"功能重复 | 不做 |

**推荐 A**，理由：Beancount 文本没有 uuid，合并无法可靠判重（重复导入就会产生重复交易）；新建账本天然隔离、可回退（导错了删掉账本即可）、符合"从别处迁移进来"的真实场景。

### D-3 导入的语法覆盖

| 方案 | 覆盖 | 遇到不支持时 | 推荐 |
|---|---|---|---|
| **A. 严格子集** | 自家导出用到的指令：`option` / `commodity` / `open` / `close` / `price` / 交易块（含 metadata） | **整体拒绝**，列出全部错误行号 | ✅ **推荐** |
| B. 宽松跳过 | 同上 + 跳过未知指令 | 跳过并警告 | 会造成静默丢数据 |
| C. 全语法 | 含 cost/price 注解、pad、balance | — | 工作量大，归 M4 |

**推荐 A**，理由：自家导出的文件必然 100% 落在子集内；而外部文件若含不支持的语法，**跳过等于悄悄丢账**——宁可整体拒绝并告诉用户第几行不支持。

## 四、恢复方案（M2 主线）

### 4.1 两阶段设计：预检 → 执行

这是防误操作的核心。**预检不改动任何数据**，只回答"这个备份里有什么、会覆盖掉什么"。

```
POST /api/backup/restore/preview   → 只读预检，返回摘要
POST /api/backup/restore           → 真正执行（需前端二次确认）
```

**预检返回**：

```json
{
  "source": "ledger-20261103-030000.db",
  "valid": true,
  "backup": { "users": 3, "ledgers": 2, "accounts": 48, "transactions": 1263 },
  "current": { "users": 2, "ledgers": 1, "accounts": 36, "transactions": 890 },
  "schema_version": "007",
  "warnings": ["备份还原后需用备份中的账号重新登录"]
}
```

**预检校验项**（任一不过则 `valid=false` + 原因）：

| 检查 | 不通过时的处理 |
|---|---|
| 文件可打开为 SQLite | 拒绝：不是有效的数据库文件 |
| 含核心表（users/ledgers/accounts/transactions） | 拒绝：不是本系统的备份 |
| `PRAGMA integrity_check` == ok | 拒绝：文件已损坏 |
| `schema_migrations` 版本 ≤ 当前版本 | 拒绝：备份来自更新版本，降级会丢列 |
| 文件大小上限（默认 512MB） | 拒绝：超出限制 |

### 4.2 执行流程

```
1. 管理员权限校验
2. 再次校验（防预检与执行之间文件被替换）
3. 【安全网】自动快照当前库，trigger=pre-restore
     失败 → 中止，不动任何数据
4. ATTACH 备份库
5. 事务内逐表替换（列取交集，兼容旧 schema 备份）
6. 校验：integrity_check + 行数与预检一致
7. COMMIT（任一步失败 → ROLLBACK，数据保持原样）
8. 重新跑迁移（备份若为旧 schema，补齐新增列/表）
9. 返回结果 + 提示重新登录
```

**列交集**（关键细节）：旧备份可能缺 `sort_order`、`icon`、`is_admin` 等后加的列。直接 `SELECT *` 会因列数不符失败。

```sql
INSERT INTO main."accounts" (id, ledger_id, uuid, name, ...)   -- 只列两边都有的
SELECT id, ledger_id, uuid, name, ... FROM bak."accounts"
```

缺失的新列由表默认值填充，随后靠第 8 步迁移补齐语义。

### 4.3 端点

| 端点 | 方法 | 权限 | 说明 |
|---|---|---|---|
| `/api/backup/restore/preview` | POST | 管理员 | 预检，body `{name}` 或 multipart 文件 |
| `/api/backup/restore` | POST | 管理员 | 执行还原 |

上传走 multipart，限制 512MB，落临时文件（`os.CreateTemp` 在备份目录同级），用完即删。

## 五、导入方案（M2 主线）

### 5.1 解析范围（严格子集）

| 语法 | 示例 | 处理 |
|---|---|---|
| option | `option "title" "家庭账本"` | 取 title / operating_currency |
| commodity | `2026-11-01 commodity CNY` | 建币种 |
| open | `2026-11-01 open Assets:Cash:CNY CNY` | 建账户 |
| close | `2026-11-02 close Assets:OldCard` | 设 close_date |
| price | `2026-11-01 price CNY 7.20 USD` | 建价格记录 |
| 交易头 | `2026-11-02 * "早餐"` | 建交易 |
| 交易带 payee | `2026-11-02 * "老板" "午餐"` | payee + narration |
| posting | `  Assets:Cash:CNY  -12.50 CNY` | 建分录 |
| metadata | `  tags: "餐饮 出差"` | 映射 tags；其余存备注 |

**明确不支持**（遇到即整体拒绝）：`include` / `plugin` / `balance` / `pad` / `note` / `document` / `event` / `custom` / cost 注解 `{...}` / price 注解 `@`。

### 5.2 解析器设计

纯函数、独立包（`internal/beancount`），零数据库依赖，便于单测：

```go
type ParseResult struct {
    Title        string
    Currency     string
    Commodities  []Commodity
    Accounts     []Account      // open/close
    Prices       []Price
    Transactions []Transaction  // 含 postings 与 tags
    Errors       []ParseError   // 行号 + 原因，全部收集完再返回
}
func Parse(text string) (*ParseResult, error)
```

**错误策略**：扫描完整文件、收集所有错误再一次性返回（不是遇到第一个就退出），这样用户一次就能看到全部问题。

### 5.3 写入策略

- 新建账本（默认名取 `option "title"`，重名自动加序号）
- 账户按 Beancount 层级名直接建（`Assets:Cash:CNY` 原样，不做父子推断）
- 交易生成 uuid + 写 `sync_log`（保证多端同步可见）
- 导入在一个大事务内完成，中途失败整体回滚，不留半个账本

### 5.4 幂等

新建账本天然隔离。额外加一道**重复导入提示**：预检时若存在同名账本 + 相同交易数，提示「疑似重复导入」，但不阻断（用户可能确实想导入两次）。

## 六、任务拆解

| 编号 | 任务 | 内容 | 估时 |
|---|---|---|---|
| **M2-a** | 恢复核心 | `internal/restore` 包：预检（校验 5 项）+ 执行（快照→ATTACH→替换→校验→迁移）；含关键单测 | 1.5 天 |
| **M2-b** | 恢复端点 | preview / restore 两端点 + multipart 上传 + 大小限制 + 临时文件清理 | 0.5 天 |
| **M2-c** | 恢复前端 | 预检摘要卡（覆盖前/后对比）+ 二次确认（需输入 `RESTORE` 解锁）+ 结果提示重新登录 | 0.5 天 |
| **M2-d** | Beancount 解析器 | `internal/beancount` 纯函数包 + 全语法子集的单测（含错误行号用例） | 1.5~2 天 |
| **M2-e** | 导入服务 | 解析结果落库（新账本 + 账户 + 交易 + sync_log，大事务）+ 端点 | 1 天 |
| **M2-f** | 导入前端 | 上传/粘贴文本 + 解析结果预览（账户数/交易数/错误列表）+ 执行 | 0.5 天 |
| **M2-g** | 联调验收 | round-trip 测试（导出→导入→再导出，bean-check 通过）、恢复 e2e、文档 | 0.5 天 |

**合计：约 6 天**（估算，含自测）

> 原路线图估 2~3 天偏低，主要低估了 Beancount 解析器（M2-d 占近 1/3）。

## 八、验收标准

### 恢复

- [ ] 预检不改动任何数据（预检前后行数一致）
- [ ] 损坏文件 / 非本系统文件 / 未来版本备份 均被拒绝且原因明确
- [ ] 还原后 `bean-check` 通过
- [ ] 还原后行数与预检摘要完全一致
- [ ] 还原前自动生成 `pre-restore` 快照，可再还原回去
- [ ] 还原中途失败（注入错误）→ 数据保持原样
- [ ] 旧 schema 备份（缺列）能成功还原，且迁移补齐
- [ ] 非管理员访问两个端点返回 403

### 导入

- [ ] 导入自家导出的文件 → 账户数/交易数/金额与源文件一致
- [ ] **round-trip**：导出 → 导入 → 再导出，两次导出文本等价且都过 `bean-check`
- [ ] 含 `plugin` / `include` / cost 注解的文件 → 整体拒绝，错误列表含行号
- [ ] 语法错误文件 → 一次列出全部错误行（不是只报第一个）
- [ ] 导入失败不留半个账本（事务回滚）
- [ ] 导入的账本能被其他成员看到（sync_log 已写）

## 九、执行顺序

```
M2-d（解析器，纯函数、无依赖、可先做）
   ↓
M2-a（恢复核心）→ M2-b（端点）→ M2-c（恢复前端）
   ↓
M2-e（导入服务）→ M2-f（导入前端）
   ↓
M2-g（round-trip 与 e2e 验收）
```

**为什么解析器排第一**：它是纯函数、零依赖、最容易独立验证，且是导入链路唯一的高风险未知项。先把它啃掉，后面的都是常规 CRUD。

**中途可交付点**：
- M2-a/b 完成 → 恢复已可用（前端没做也能靠 curl 恢复）
- M2-d 完成 → 解析能力可独立验证（对任意 .beancount 文件试解析）
- M2-e 完成 → 导入链路通
